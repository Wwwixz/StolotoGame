# СтолоПлей — быстрые игровые комнаты на бонусные баллы (MVP)

Демо-прототип веб-приложения «Быстрые игровые комнаты» для VIP-аудитории «Столото»
(кейс Кубка России по продуктивному программированию). Пользователь задаёт параметры
подбора комнаты, система подбирает (или мгновенно создаёт) комнату, резервирует
бонусные баллы, после таймера заполняет места ботами, проводит розыгрыш **на бэкенде**
(взвешенный ГСЧ с учётом бустов) и показывает раунд как живую трансляцию лототрона.

**Визуальная оболочка — лототрон:** каждый участник — нумерованный лотерейный шар
в стеклянной сфере; результат определяется backend-логикой, оболочка только
транслирует процесс (запуск → анимация → приближение к финалу → победитель).

## Стек

| Слой | Технологии |
| --- | --- |
| Backend | **Java 17**, Spring Boot 3.3 (Web, WebSocket, Data JPA, Validation), SecureRandom |
| БД | **PostgreSQL 16** (профиль `local` — H2 для запуска без Docker) |
| Frontend | **React 18 + TypeScript**, Vite, React Router 6, Canvas API (лототрон) |
| Real-time | Нативный **WebSocket** (`/ws`, JSON-протокол) + fallback-опрос REST |
| Инфраструктура | **Docker Compose**: postgres + backend + frontend (nginx) |

## Запуск

### Всё сразу через Docker (рекомендуется)

```bash
docker compose up --build
```

Приложение: **http://localhost:8080** (frontend-nginx, API и WebSocket проксируются).
Прямой доступ к API для экспертов: http://localhost:8081/api/rooms

### Без Docker (быстрый старт на H2)

Нужны JDK 17 и Maven (или Docker только для БД):

```bash
cd backend
mvn spring-boot:run -Dspring-boot.run.profiles=local   # backend на :8080, встраиваемая H2

cd ../frontend
npm install
npm run dev                                            # фронт на :5173, прокси на :8080
```

Продакшн-сборка фронта: `npm run build` (выход в `dist/`).

### Тесты

```bash
cd backend && mvn test
```

Юнит-тесты ГСЧ/весов и экономики + сквозной тест игрового цикла
(резерв → буст → боты → розыгрыш → выплаты → журнал) на встраиваемой H2.

## Роли и экраны

На `/` выбирается роль (сохраняется в localStorage).

**Пользователь:** `/lobby` — лобби с живыми комнатами; `/games` — список с фильтрами
и сортировкой; `/auto-match` — автоподбор по параметрам (создаст комнату, если ничего
не нашлось); `/rooms/:id` — живая комната (вход с резервом → ожидание и таймер →
боты → розыгрыш-лототрон → победитель); `/history`, `/balance`, `/profile`.

**Администратор:** `/admin` — конфигуратор комнат с живым анализом экономики
и управлением открытыми комнатами; `/economy` — «что если»-калькулятор и сравнение
комнат по данным backend; `/log` — журнал раундов с proof-of-RNG.

В шапке — переключатель тестовых игроков (баланс, VIP-статус, резерв).

## Игровая механика (как в ТЗ)

1. **Подбор комнаты.** Пользователь задаёт цену входа, число мест, мин. процент фонда,
   наличие буста → система подбирает подходящую открытую комнату (приоритет: живые →
   ближе по местам → заполненнее → дешевле). Если подходящей нет — **мгновенно создаёт**
   новую под запрос: игрок не ждёт начала игры.
2. **Резерв баллов.** При входе цена входа списывается с доступного баланса и резервируется
   до конца раунда. Выход до старта возвращает резерв.
3. **Таймер ожидания.** Стартует с первым участником (по умолчанию 60 сек, настраивается
   15–300). Полная комната стартует через 5 секунд, не дожидаясь таймера.
4. **Боты.** После таймера движок заполняет свободные места ботами (по одному за тик —
   видно в реал-тайме). Боты — отдельный тип участников в UI, занимают места и могут
   побеждать: **если побеждает бот, приз остаётся в системе**.
5. **Буст.** Один на раунд, покупается до старта за баллы (+цена в доход системы),
   увеличивает вес участника при выборе победителя. Механика прозрачна: в комнате
   показаны веса всех участников и вероятность победы с бустом и без.
6. **Победитель — только на бэкенде.** `WinnerService`: вес = 1 (с бустом — 1 + эффект),
   ГСЧ — `SecureRandom`, победитель — участник, в чей накопленный диапазон весов попало
   значение ГСЧ. Раунд логируется сидом, значением ГСЧ и диапазонами (proof-of-RNG).
   Пока идёт анимация (`RUNNING`), результат по API не раскрывается.
7. **Выплаты.** Фонд = занятые места × цена входа; победителю — `фонд × процент фонда`,
   остаток — доход системы (управляемая экономика: см. анализ в конфигураторе).
8. **Комбинация.** По итогу раунда генерируется выигрышная комбинация (4 числа из 36 +
   номер шара победителя) — бонусная сущность, отображается в UI и журнале.

## Параметры игры (для организаторов)

Меняются в конфигураторе `/admin` и влияют на механику:

- **Количество мест (2–10)** — размер комнаты, базовая вероятность `1/места`;
- **Цена входа** — сколько резервуется при входе, формирует фонд;
- **Процент фонда (50–100)** — доля взносов победителю; >97% — сохранение блокируется
  (убыточно для организатора), <70% — предупреждение (отпугивает игрока);
- **Буст: вкл/выкл, цена, эффект** — анализатор считает «справедливую цену»
  (призовой фонд × вероятность × эффект) и предупреждает, если буст убыточен системе
  или слишком дорог для игрока;
- **Таймер ожидания (15–300 сек)** — как долго комната собирает живых игроков.

Анализ показывает: взносы за раунд, призовой фонд, доход системы, EV игрока,
справедливую цену буста и предупреждения (хороший/риск/блок).

## Архитектура и масштабирование

- **Состояние** хранится в PostgreSQL (комнаты, участники, раунды, транзакции) —
  backend переживает рестарт; `ddl-auto=update` для MVP.
- **Real-time.** Комната транслируется по WebSocket-каналу `room:{id}`; лобби — канал
  `lobby`. Клиент считает таймер локально от `phaseEndsAt − serverTime`, при обрыве
  переходит на опрос REST. На масштабе канал выносится в Redis pub/sub или Kafka,
  клиенты балансируются sticky-сессией (или маркер канала в JWT).
- **Игровой движок.** В MVP — однопоточный шедулер в приложении (тикает 400 мс,
  переводит комнаты OPEN → RUNNING → FINISHED). Для горизонтали: вынос тика в
  отдельный сервис-шедулер с распределённой блокировкой комнаты (ShedLock/лидер-элекшн)
  либо событийная модель: таймеры в отложенной очереди (Redis ZSET / Kafka), состояния
  комнат — атомарные переходы в БД. Идемпотентность переходов уже заложена
  (`settled`-флаг, проверка статуса в сервисе).
- **Экономика.** Все операции балансов — транзакционные записи (резерв/списание/буст/
  выигрыш) с `balanceAfter` — журнал сверяем; доход системы считается по раундам
  (доля системы + бусты + невынутые призы ботов), рост обязательств контролируется
  анализатором конфигураций.
- **Изоляция раундов.** Победитель вычисляется до начала анимации и скрывается от API
  до финала; жульничество через клиент исключено (оболочка получает только факт).

## Встраиваемость в контур «Столото»

Модуль спроектирован как встраиваемый: регистрации нет — личность игрока и баланс
приходят извне. Точки интеграции:

- **Кошелёк.** `WalletService` — единственное место операций с балансом
  (reserve/refund/spend/credit); в контуре заменяется вызовами API бонусного счёта ЛК.
- **Профиль.** `Player` — минимальный снимок (id, имя, VIP-статус); в проде подменяется
  SSO/токеном ЛК, VIP-статус влияет на доступ к комнатам (уровни входа).
- **API раунда.** `/api/winner/preview` и `/api/journal` дают аудит и внешние проверки;
  тот же контракт подходит для сервер-ту-сервер запуска раунда внешним сервисом.
- **История.** Участия и операции уже пишутся в нормализованном виде — синхронизация
  с историей ЛК сводится к вебхукам по `Transaction` и `RoundRecord`.
